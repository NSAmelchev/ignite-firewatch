# controller — очередь, сборка коммитов, ABBA-статистика, API и UI

Один JVM-процесс (`controller.jar`, `-Xmx128m` хватает), который:

- держит bare-зеркало `apache/ignite` (`GitMirror`, git CLI; ветки и теги — на каждом опросе, `pr/N` — по запросу);
- следит за веткой (`Watcher`): новые коммиты после watermark → задачи по политике автозапуска;
- собирает `ignite-core` коммита с upstream-модулями (`Builder`), кладёт runtime-classpath в `cache/artifacts/<sha>/libs`;
  сценарию с `@Bench(modules)` (SQL) — отдельная сборка с этими модулями в `cache/artifacts/<sha>+<модули>/libs`;
- выполняет задачи одним worker'ом (`JobRunner`): сборка → фазы harness → статистика; никогда не собирает во время измерения;
- считает ABBA-вердикт (`Stats`): Δ%, bootstrap-CI, порог шума из A/A-калибровок;
- отдаёт REST API и статический UI (`Api`, `jdk.httpserver`, без фреймворков).

Хранилище — SQLite (`data/ignite-firewatch.db`, WAL) плюс файлы прогонов `data/runs/<job>/<phase>/` (result.json, series.json, логи, JFR).

## Запуск локально

```bash
mvn -q package                     # modules/harness/target/harness.jar + modules/controller/target/controller.jar
modules/harness/dev-libs.sh                # релизная ignite-core для FAKE_BUILD (и dev-libs-sql: + indexing, calcite)
IGNITE_FIREWATCH_FAKE_BUILD=1 IGNITE_FIREWATCH_PORT=8085 IGNITE_FIREWATCH_DATA_DIR=/tmp/bench/data IGNITE_FIREWATCH_CACHE_DIR=/tmp/bench/cache \
  java -Xmx128m -jar modules/controller/target/controller.jar   # UI на http://localhost:8085
```

При пустой БД UI открывается с мастера первого запуска: где запускать, репозиторий, релиз. Пока мастер не пройден, `Watcher`
ждёт и ничего не клонирует. Затем контроллер делает полный клон `apache/ignite` (≈0.5 ГБ, около 2 минут), ставит watermark на
текущий head и ничего не запускает, пока автозапуск выключен (по умолчанию выключен). `FAKE_BUILD=1` подменяет сборку
копированием релизных jar'ов — для отладки очереди и UI без Maven; harness при этом настоящий.

## Конфигурация (`config/ignite-firewatch.properties`, env `IGNITE_FIREWATCH_*` или `-Dignite.firewatch.*`)

Настройки лежат в `config/ignite-firewatch.properties` (каталог запуска; другой файл задаёт `IGNITE_FIREWATCH_CONFIG`) строками
вида `data.dir = …`. Переменная окружения `IGNITE_FIREWATCH_DATA_DIR` перекрывает строку файла, системное свойство
`-Dignite.firewatch.data.dir` перекрывает обе. В контейнере каталог `config/` смонтирован только на чтение, а пути и порт задаёт образ.

| Переменная | По умолчанию | Что |
|---|---|---|
| `IGNITE_FIREWATCH_DATA_DIR` | `data` | SQLite и результаты прогонов (ценное) |
| `IGNITE_FIREWATCH_CACHE_DIR` | `cache` | зеркало, `m2`, артефакты, рабочие каталоги сборки (можно стереть) |
| `IGNITE_FIREWATCH_HARNESS_JAR` | `modules/harness/target/harness.jar` | harness |
| `IGNITE_FIREWATCH_BIND_HOST`, `IGNITE_FIREWATCH_PORT` | `0.0.0.0`, `8090` (в контейнере 8080) | HTTP |
| `IGNITE_FIREWATCH_REPO_URL`, `IGNITE_FIREWATCH_BRANCH` | `https://github.com/apache/ignite.git`, `master` | что зеркалим и за чем следим |
| `IGNITE_FIREWATCH_JAVA`, `IGNITE_FIREWATCH_MVN` | java текущей JVM, `mvn` | исполняемые файлы для дочерних процессов |
| `IGNITE_FIREWATCH_MAVEN_HEAP_MB` | `1536` | `-Xmx` Maven при сборке коммита |
| `IGNITE_FIREWATCH_MAVEN_SETTINGS` | пусто | settings.xml для каждой сборки (`-s`): зеркала, прокси, учётные данные; относительный путь — от каталога приложения |
| `IGNITE_FIREWATCH_MAVEN_ARGS` | пусто | ещё аргументы каждого вызова mvn через пробел, после своих (например `-o`, `-gs FILE`, `-Dkey=value`) |
| `IGNITE_FIREWATCH_BUILD_TIMEOUT_MIN`, `IGNITE_FIREWATCH_FETCH_TIMEOUT_MIN` | `25`, `30` | таймауты сборки и `git fetch` |
| `IGNITE_FIREWATCH_HARNESS_HEAP_MB` | `128` | heap launcher-JVM harness (узлы и loader — по сценарию) |
| `IGNITE_FIREWATCH_PHASE_GRACE_SEC` | `120` | запас сверх собственного худшего времени harness, после чего фаза считается зависшей |
| `IGNITE_FIREWATCH_FAKE_BUILD`, `IGNITE_FIREWATCH_FAKE_LIBS_DIR` | `0`, `modules/harness/target/dev-libs` | режим разработки |
| `IGNITE_FIREWATCH_SSH_KEY`, `IGNITE_FIREWATCH_SSH_KNOWN_HOSTS` | пусто: что найдёт сам ssh; в контейнере `/ssh/key` и `/ssh/known_hosts` | ключ и `known_hosts` удалённого стенда, в БД не хранятся |
| `IGNITE_FIREWATCH_SSH_ACCEPT_NEW_HOSTS` | `false` | `true`: ssh принимает ключ хоста, которого нет в `known_hosts`, при первом входе и дописывает его туда (`StrictHostKeyChecking=accept-new`); сменившийся ключ не принимается всё равно |

Настройки, которые меняются из UI (таблица `settings`, засеваются при первом старте):
`autorun.enabled` (false), `autorun.mode` (`abba-vs-parent` | `single`), `autorun.scenario` (один или несколько
сценариев через запятую, задача на каждый; первый — сценарий по умолчанию для страниц и API; на стенде
`putget-thin-t16,putget`),
`autorun.pathFilter` (globы: `modules/core/src/main/**`, …, `pom.xml`, `**/pom.xml`), `autorun.maxBacklog` (5), `autorun.keepDays` (1),
`watch.pollSec` (3600), `watch.watermark`, `retention.keepJfrJobs` (30), `retention.artifactsGb` (3),
`calibration.*` и `master.*` (A/A и master vs релиз: `mode` `off` | `keep`, `keepDays` (7), `scenarios`; по умолчанию
выключены), `notify.*` (см. ниже).

## Стенд (`Stand`)

Один экземпляр приложения — один стенд. `local`: все JVM на этой машине. `remote`: JVM на Linux-хостах по ssh, у хоста адрес,
пользователь, порт ssh, роль (`servers` или `loaders`), JDK 17, рабочий каталог и по желанию адрес данных для трафика узлов. Нужен
хотя бы один хост каждой роли, один адрес нельзя указать дважды. Значения попадают в командную строку ssh, поэтому проверяются
строго. На `remote` контроллер кладёт в каталог фазы `stand.json` и передаёт его harness'у (`--stand`), дальше работает harness, см.
[его README](../harness/README.md#удалённый-стенд). Коммиты по-прежнему собирает контроллер.

**Check** (`POST /api/stand/check`, контроллер вызывает `harness.jar check`) проверяет сохранённый или только что введённый стенд. Падает на
ssh, JDK ниже 17, диске меньше 5 ГБ, памяти меньше 2 ГБ, чужих JVM, недоступных портах Ignite между хостами и расхождении часов от секунды;
предупреждает про часы от 100 мс, swap, THP `always` и CPU governor не `performance`. На `local` чужая JVM только предупреждение: это может быть
среда разработки. Проверка занимает порты Ignite, поэтому идёт при пустой очереди и одна: задача, поставленная за это время, ждёт её конца. Пройденный Check незамороженного стенда запоминает отпечаток
каждого хоста (CPU, ядра, память в ГБ, ядро ОС, JDK), и без него задача на `remote` не стартует. Перед каждой фазой harness сверяет хост с отпечатком:
при расхождении фаза падает с указанием, что изменилось, и в историю ничего не попадает. Заморозка касается и отпечатка, повторный Check после неё
только показывает состояние.

**Размеры** (`sizes`): память узла, заполнение data region и множитель потоков. Без памяти сценарии берут числа из своего кода, и командная строка
фазы не меняется: так работают все стенды, настроенные раньше. С памятью harness делит её на резерв (10 %, не меньше 256 МБ), heap (35 % остатка,
у SQL 50 %, не меньше 256 МБ) и регион, а число ключей и строк выводит из региона. Check предлагает размеры: память самого слабого хоста серверов под самый большой
сценарий, потоки по числу CPU загрузчика. Если введённая или предложенная память узла на такой хост не помещается, отчёт об этом предупреждает
(`sizesWarning`). Отчёт также называет хосты, которые проверял (`checked`): мастер не принимает его после правки хоста. Таймаут preload растёт вместе с объёмом.

**Measure load** (`POST /api/stand/measure`) ставит задачу типа `probe`: главный сценарий на голове ветки с ×1, ×2 и ×4 потоками, 15 с прогрева и 45 с
замера каждый, пока throughput растёт хотя бы на 10 %. Итог лежит в `stand.load`, страница предлагает применить его. Такие задачи не попадают в
историю ветки и не замораживают стенд. После заморозки кнопки нет.

**Зачистка.** Harness убирает за собой сам, в том числе при SIGTERM. Если он убит жёстко, JVM остаются на хосте: их снимает следующая фаза, контроллер
при старте и после задачи, закончившейся не `done`, а также кнопка Clean hosts (`POST /api/stand/sweep`). Метка запуска и каталог фазы начинаются с
префикса стенда, поэтому JVM и фазы другого стенда на том же хосте это не трогает. Префикс выводится из каталога данных и `stand.instance`, случайного
значения, которое выбирается один раз и хранится в БД: каталог данных у всех контейнеров один и тот же, `/data`. Зачистка при старте идёт в потоке
worker до первой задачи, так что молчащий хост задерживает очередь, а не запуск приложения.

Выбор живёт в `stand.*`, пишет его только `PUT /api/stand`, через `PUT /api/settings` его не поменять. Первая завершённая фаза замораживает
стенд: результаты разных стендов не смешиваются, другой стенд это другой экземпляр со своим каталогом данных. Упавшая фаза не замораживает,
чтобы неверные хосты можно было поправить. Стенд с задачами из прошлых версий считается `local`, мастер ему не показывается.

## Задачи

- `single` — одна фаза `S` для ref A. `abba` — фазы `A1 B1 B2 A2`: A — baseline, B — target. `probe` — Measure load, фазы `x1 x2 x4`.
- Источник: `manual` (UI/API), `auto` (watcher), `calibration` (A/A: один и тот же sha с обеих сторон), `compare`
  (вкладка Compare: ручная отладка, в историю ветки не попадает), `release` (master против релизного тега), `bisect`
  (шаг автобисекта: обычный сегмент или коммит против родителя, в истории ветки как все).
- Ref'ы резолвятся в sha при постановке (`master`, `master~3`, sha или префикс, тег `2.17.0`, `pr/13706`, ссылки
  GitHub `…/pull/N`, `…/pull/N/commits/SHA`, `…/commit/SHA`, `…/tree/BRANCH`, `…/releases/tag/TAG`);
  задача с теми же sha, типом и сценарием, пока она в очереди или идёт, не дублируется.
- Приоритет: выше — раньше; авто = 0, ручные по умолчанию 1. Статусы: `queued → running → done | failed |
  cancelled | interrupted` (последний — рестарт контроллера во время задачи).
- Автозапуск: watermark стартует с head на момент первого опроса и всегда двигается вперёд; коммиты, пришедшие на
  паузе, отфильтрованные по путям или не влезшие в `maxBacklog`, остаются доступными для ручного запуска со страницы
  Commits (кнопка Run = ABBA против родителя).
- Cancel убивает текущий процесс и всех потомков (`ProcessHandle.descendants`), плюс добивает JVM по маркеру
  `-Dignite.firewatch.run=<стенд>-job<id>-…`, где `<стенд>` — хэш пути `IGNITE_FIREWATCH_DATA_DIR`. При старте контроллер переводит `running` в
  `interrupted`, незавершённые сборки — в `failed`, и убивает JVM с маркером своего стенда; чужие на той же машине не трогает.
- Артефакты сборок вытесняются по LRU сверх `retention.artifactsGb`, кроме нужных активным задачам.
- После каждой задачи лог прогона больше 20 МБ обрезается до первых и последних 5 МБ с пометкой посередине. Узел, который
  пишет в лог каждый упавший запрос, набирает сотни МБ за фазу. Файлы прогонов API отдаёт потоком, хвост лога задачи читается с конца.
- Если harness умер, не записав `result.json`, ошибка фазы берёт последнее исключение из `harness.log` (`the harness died: …`).
  «harness did not start?» остаётся только для случая, когда в логе нет ни одного исключения.

### Что требует внимания (`Attention`)

Матрица дашборда сверяет последний прогон master vs релиз с тем, что найдено на ветке. Найденным считаются прогоны «коммит
против родителя» с вердиктом по метрике и находки бисектов, поэтому ручной Split тоже засчитывается. Если сумма их Δ
совпадает с Δ master в пределах порога, метрика `explained`: кроме этих коммитов ничего не сдвинулось. Если нет, остаток
показан как `partial`, в том числе когда бисект нашёл коммит, а master его уже не показывает. Без найденных коммитов статус
даёт последний бисект этой метрики (`running`, `stopped`, `spread`, `lost`), а если его не было, метрика `unexplored`.
Бисект идёт по одной метрике, но каждый шаг измеряет все: если какой-то прогон сегмента сдвинул метрику в ту же сторону, что и
master, она `narrowed`, показан самый короткий такой сегмент, и бисект запускается от него, а не от всего диапазона.
Бисекты сравнений другой диапазон, здесь они не учитываются. Прогон ветки новее master vs релиз идёт отдельной строкой `new`.
Кнопка Bisect deviations запускает нужные поиски разом: сценарий в окне идёт одной строкой с выбором метрики, суженная метрика
стартует от своего сегмента, чёткий сигнал выбран заранее, слабый только предложен. На сценарий допускается один активный бисект
(ветки или сравнения), поэтому занятый сценарий стоит в конце окна неактивной строкой `after #N`, и та же пометка заменяет
кнопки в деталях ячейки и в Still open.
Сначала идёт то, что требует действий, полностью объяснённые сценарии свёрнуты. `start ms` и `preload ms` сюда не попадают:
это шум запуска.

### Сравнения (`Comparisons`)

Сравнение — отдельная сущность: две ссылки и набор сценариев, у него есть своя страница `#/comparisons/N`. Ref'ы
резолвятся один раз при постановке, поэтому все сценарии меряют одни и те же два коммита. Каждый сценарий — обычная
ABBA-задача с `comparison_id` и источником `compare`, с приоритетом 2. В строке `comparisons` лежит только вопрос (ref'ы,
sha, подпись, приоритет); статус (`queued`, `running`, `done`, `failed`, `cancelled`), счётчики и ETA всегда считаются по
задачам. Повтор сценария остаётся в сравнении и объединяется с прошлыми прогонами только на его странице. Cancel снимает
ждущие задачи и останавливает бегущую, готовые остаются; Delete доступен, когда активных задач нет, и удаляет сравнение
вместе с задачами и файлами. Уведомление одно, когда в очереди не осталось задач сравнения; по отдельным задачам его нет.

Отклонение сравнения можно бисектить: кнопка Bisect в строке сценария, клик по Δ с вердиктом (сразу эта метрика) или
Bisect deviations для нескольких сценариев разом. Метрики в окне отсортированы по силе сигнала: Δ, делённая на разброс
фаз; меньше 3× помечено как `weak`, такой поиск редко доходит до коммита. Сценарии с вердиктом выбраны заранее, те, где
сдвинулась только отдельная метрика, предложены без галочки. Отдельной связи нет: бисект принадлежит сравнению, потому что
его корневая задача имеет `comparison_id`, и таблица не менялась. Шаги — обычные задачи бисекта, в строки сравнения они не
входят, а на Timeline и Commits попадают только коммиты самой ветки. Статус сравнения от бисектов не зависит. Cancel
сравнения снимает и активные бисекты; Delete запрещён, пока бисект активен, а закончившийся бисект остаётся и теряет только
ссылку на сравнение. Диапазон — цепочка первых родителей от A до B (`commits` в ответе API); если A не предок B,
как у релизных тегов, цепочка начинается от их merge-base, а коммиты только на стороне A не ищутся.

Для PR с пустым baseline: B — пробное слияние PR в текущую ветку, которое держит GitHub (`refs/pull/N/merge`), A — его
первый родитель, то есть тот коммит ветки, в который PR вливается. Δ показывает ровно то, что изменит слияние PR
сейчас. Нужен открытый PR без конфликтов. Для других ref'ов с пустым baseline A — merge-base с веткой, а если target уже в
ветке (merge-base совпал бы с ним самим) — его родитель; любой ref в baseline задаёт A явно. В тренд и Commits идут
только ABBA «коммит против родителя»; хэш сценария не включает `description`, так что правка описания историю не рвёт.

### Автобисект (`Bisector`)

Кнопка Bisect у готового сегмента с вердиктом по метрике (Timeline, страница задачи, ячейка матрицы на дашборде); сам стенд
бисекты не запускает. Бисект идёт во все части сегмента, которые сдвигают выбранную метрику в ту же сторону сами по
себе (вердикт метрики), самую большую |Δ| первой, и доводит каждую до коммита:

- шаг меряет левую половину участка; тихая (без вердикта и ≤ ⅓ Δ участка) — дальше правая без замера (или с готовым
  замером, если пара уже мерилась: решение по нему, а не по оценке «Δ участка − Δ левой»); иначе меряется и правая;
  каждая сдвинувшаяся половина становится открытым участком; ни одна — участок меряется ещё раз (`repeat`, объединяется
  с прежними прогонами): сдвинулся — итог ветки `spread` (несколько мелких изменений), нет — `lost`;
- на одном коммите: не мерянный меряется (`leaf`), при |Δ| < 2 порогов — ещё раз (`confirm`), итог ветки `found` или `lost`;
- итог бисекта — список находок; статус `found`, если найден хоть один коммит, иначе `spread`; ни того ни другого — проверка,
  настоящий ли был сдвиг: половины первого уровня вместе дают хотя бы половину Δ сегмента (а если правая не мерилась, то же
  про свежий прогон сегмента, шаг `root`). Настоящий — `inconclusive`: поиску не хватило точности, нет — `lost`, это был шум.
  В причине — найденные коммиты с Δ и какую долю Δ сегмента они объясняют (меньше половины — «остальное размазано или шум»);
- уже измеренные пары берутся готовыми (`reused`); одинаковая задача в очереди дожидается, а не дублируется; в очереди
  не больше одного шага бисекта, приоритет по умолчанию 2 (выше ручных);
- шаг упал или его отменили в Queue — бисект `stopped`, Resume ставит шаг снова; прерванный рестартом шаг ставится
  заново сам (`Bisector.recover()` при старте); предохранитель — `2·(2·log₂N + 4)` шагов, дальше `stopped`;
- Cancel: новых шагов нет, ждущий шаг снимается, бегущий останавливается (или доживает), готовые шаги остаются
  обычными прогонами, по флажку удаляются; шаг активного бисекта удалить нельзя (`DELETE` → 400).

Состояние — строка таблицы `bisects` (JSON `state_json`: открытые участки, находки, шаги с решениями), шаги — задачи
с `bisect_id`/`bisect_step` (миграция схемы v2). Уведомление — одно, когда бисект закончился или встал.
Постепенный спад из кусков меньше порога шума до коммитов не раскладывается: бисект закончит его как `spread` на том
участке, где половины перестают сдвигаться сами по себе.

**Долгий поиск** (`Bisector.deep`, кнопка Deep search у бисекта со статусом `inconclusive`, `spread` или `lost`) нужен, когда
сдвиг близок к шуму. Одна задача ABBA меряет с ошибкой порядка фазы (около 1 %), поэтому при сдвиге в 2 % и пороге в 2 %
быстрый поиск часто теряет ступеньку: половина с ней не берёт порог, а спокойная левая половина уводит его вправо без
замера. Сам стенд долгий поиск не запускает. Он идёт в том же бисекте, сверху сегмента, и всё уже измеренное идёт в дело:

- на каждом уровне меряются обе половины, и решение принимается сравнением их между собой (`deepChoice`), а не порогом:
  половина несёт сдвиг, если даёт от половины порога шума и обгоняет вторую минимум на столько же, даже без вердикта;
- спорное решение получает ещё прогоны, до `DEEP_RUNS` (4) на половину, потом выбирается бо́льшая половина; если обе несут
  по части, ищутся обе: это два изменения;
- ветка стоит часов, поэтому перед входом в неё диапазон перемеряется (`holds`): при сдвиге от порога хватает двух прогонов,
  ближе к шуму нужно четыре, ветка меньше половины порога закрывается как `lost`, явный сдвиг в два порога входит сразу.
  Каждая ветка получает свой запас шагов;
- Δ пары — медиана по прогонам (`JobService.medianResult`); прогон с фазами, разошедшимися больше чем на 2,5 порога шума,
  не считается, а пара, у которой ничего другого нет, перемеряется;
- коммит должен удержать половину порога на 4 прогонах (явному сдвигу в два порога хватает двух), иначе итог ветки `spread` на
  самом коротком участке, который ещё двигался; два уровня подряд без половины, несущей сдвиг, заканчивают ветку так же.

Цена на сегменте из 657 коммитов — в симуляции около 27 задач (порядка 4 часов), ступенька 2,3 % при шуме 0,9 % находится в
96 % случаев, 1,6 % на 41 коммите — в 80 %; предохранитель `6·log₂N + 8` шагов сверх уже сделанных. Плавный спад
без отдельной ступеньки честно заканчивается `spread`. Повторный обычный бисект того же сегмента этого не заменит: он
возьмёт те же измеренные пары и пройдёт тем же путём.

## Статистика ABBA (`Stats`)

Для каждой метрики A = mean(A1, A2), B = mean(B1, B2), Δ = B/A − 1. Вердикт метрики `regression | improvement |
no-change` требует одновременно:

1. |Δ| > порог, где порог = max(шум A/A по метрике, разброс между повторами одной стороны |A1−A2|/A и |B1−B2|/B);
2. для метрик с посекундными рядами (throughput, p99) — 95 % CI Δ по moving-block bootstrap (блок 5 с, 2000 итераций)
   не содержит 0.

Шум A/A: p95 |Δ| по последним 10 калибровкам сценария (нужно ≥ 3), не ниже дефолта метрики (throughput 2 %, p50 3 %,
p99 5 %, p99.9 10 %, alloc 3 %, CPU 4 %, GC pause 15 %…). Вердикт задачи — по throughput, p99 и «CPU сервера на
операцию» (`serverCpuUsPerOp` = CPU серверных JVM × число CPU / throughput: рост серверной стоимости виден даже когда
throughput ограничен клиентом); остальные метрики (GC, аллокации на операцию, CPU, heap) показываются с собственными
вердиктами. Всё это лежит в `jobs.comparison_json`.

**Повторы.** Завершённые ABBA-задачи ветки с тем же A, B, сценарием и хэшем сценария объединяются: A — среднее всех
фаз A, B — всех фаз B, CI — по всем посекундным рядам; разброс повторов — максимум внутри одной задачи (дрейф стенда
между днями в порог не попадает), шумовой пол прежний. Результат кэшируется (LRU на 500 записей).

**Диагностика без вердикта:** `serverStartMs` (время внутри `Ignition.start()`, самый медленный узел), `preloadMs`.

1.6.32 (`vendor/`). Меню: Dashboard · Timeline · Commits · Compare · Bisects · Queue | Noise · Scenarios · Settings (правая группа прижата вправо), справа поле поиска: sha, `IGNITE-123`, `#PR`, ссылка на GitHub, номер задачи, бисекта или сравнения, слова из темы коммита, `/` ставит в него курсор. Вкладка меняется сразу, поэтому пока страница грузится, сверху идёт полоса и старая страница притушена.

Заливка у Δ только там, где метрика решает вердикт задачи (ops/s, p99, CPU/op) или это метрика, за которой идёт бисект; остальные сдвиги мягким фоном. Колонки метрик везде одни: ops/s, p99 µs, CPU µs/op, alloc KB/op. Номера тикетов и PR в темах коммитов ведут в трекер и на GitHub. То, что таблица сворачивает как спокойное, остаётся видно зелёной строкой с названиями. Диалоги устроены одинаково: заголовок, тело с одной колонкой подписей, снизу итог и кнопки; необратимое действие красным. Выбор бисектов это таблица: сценарий, метрика, Δ, сила сигнала, коммиты.

- **Dashboard** — ответ на вопрос «всё ли в порядке с master». Сверху полоса стенда: Worker, Queue, Last commit, Noise,
  Auto-run; пока идут бисекты, плитка Queue показывает, когда закончатся все. Ниже одна матрица master vs релиз: строка на

  Automation: что стенд запускает сам, три карточки одного вида. On new commits: выключено, сегменты, каждый коммит или одна фаза, сценарии,
  фильтр путей. Сегменты, A/A и master vs релиз живут по одному правилу `Freshness`, настраивается только срок: Keep fresh, every N days (1 для сегментов, 7 для остальных). Моложе срока ничего не идёт. Старше идёт, когда стенд простоял 2 часа, с низким приоритетом. Вдвое старше срока идёт несмотря на очередь, впереди следующих шагов бисектов. Сегмент считает возраст от самого старого неизмеренного коммита, A/A и master vs релиз по каждому сценарию. A/A, которых меньше 3 для своего порога, добираются сразу, а master vs релиз пропускается, если новых коммитов нет. У каждого свой набор сценариев, новый сценарий попадает в «все» сам. Пока стенд закрыт на обслуживание, ничего не стартует, пропущенный запуск уходит после открытия.
  Repository: адрес git и основная ветка. Значения живут в БД, `IGNITE_FIREWATCH_REPO_URL` и `IGNITE_FIREWATCH_BRANCH` только задают их при первом запуске.
  Смена проверяется по `git ls-remote`, требует пустой очереди и сразу применяется: стенд идёт от новой головы, прогоны старой ветки
  остаются в БД, но уходят с Commits и Timeline. Ссылки на коммиты и PR строятся от этого адреса. Режимы автозапуска описаны прямо в разделе.
  Release: с чем дашборд сравнивает master. Пусто значит самый старший тег X.Y.Z, маска `2.18.*` выбирает старший подходящий, можно
  указать любой тег, sha или ветку. Значение проверяется при сохранении; прогоны против другого релиза на дашборде не считаются.
  Разделы переключаются без обращения к серверу, несохранённый ввод не теряется. Limits, рядом с лимитами оценка занятого ими места: сколько хранить сравнений и закончившихся
  бисектов (0 = все, по умолчанию; при уменьшении лимита страница спрашивает подтверждение), тяжёлые файлы последних N задач, кэш
  сборок, очередь автозапуска. История ветки не ограничивается: на ней стоят Timeline, повторы и пороги шума.
- **Noise** — строка на сценарий: Δ последней A/A по ops/s, p99 и CPU/op отдельными колонками, сколько калибровок (`2 of 3`, пока
  своих порогов нет), раскрывается история. Кнопка добирает A/A там, где их меньше трёх, вторая запускает все сценарии.
- **Queue** — компактный блок текущей задачи с Log и Cancel, очередь с приоритетами, ожидаемым стартом и длительностью
  каждой задачи, когда закончится то, что ждёт сейчас, и когда закончатся бисекты (они добавляют шаги по одному), активные
  бисекты, история с флажком «without bisect steps»; шаги помечены «bisect #N · step k».
- **Bisects** (`#/bisects`) — все бисекты: активные сверху, чипы All, Active, Needs a deep search, Found, No single commit (выбор
  виден в адресе). Повторный поиск того же участка той же метрики идёт одной строкой, прежние номера рядом; так же в Comparison.
- **Bisect** (`#/bisects/<id>`) — показатель в заголовке и с расшифровкой, карта поиска в цветах Timeline: сверху весь сегмент, ниже диапазоны всё уже, полосой то, что ещё под подозрением, линиями и обводкой найденные коммиты (клик ведёт в задачу блока, перетаскивание увеличивает); сегмент и его Δ, открытые участки, итог или причина остановки, таблица находок
  (коммиты, размазанные участки, неподтвердившиеся), таблица шагов (что мерили, задача или reused, Δ, вердикт,
  решение); в долгом поиске строка на пару с Δ каждого прогона, быстрый поиск свёрнут. Cancel/Resume/Deep search, Delete у закончившегося, ссылка на Timeline.
- **Timeline** — сверху обзор всех сценариев на одной шкале коммитов с релиза: строка на сценарий показывает, где master сейчас. Штриховка: самый короткий прогон с вердиктом, сдвиг где-то внутри него; сплошная риска: один коммит. Бледная заливка после сдвига: он всё ещё в силе. Заливку определяет только прямой замер master vs релиз справа, поэтому сдвиг, который ушёл, остаётся штриховкой без заливки, а если master сдвинут, но ни один прогон этого не показал, штриховка идёт через всю строку; спокойные прогоны синие; клик по строке открывает сценарий, клик по блоку ещё и его прогон. Из меню открывается только обзор: детали появляются по клику на строку, закрываются повторным кликом или кнопкой. По ссылке на конкретный сценарий (Dashboard, Commits, Bisect) наоборот: детали открыты, обзор свёрнут. Ниже карта сценария: ряды по размеру, Δ на широких блоках. Сценарий, метрика, зум и выбранный блок в адресе (ссылкой можно делиться), уточнённые сплитом блоки бледнее, у активного бисекта —
  плашка над картой и по пунктирной полосе через все ряды на каждый участок, который он ещё ищет.
- **Job** — таблица ABBA (фазы, A, B, Δ, CI, порог, вердикт): метрики вердикта и alloc/op, остальные по кнопке; вердикт только у метрик, которые его решают. Провальная фаза помечена. Наложенные посекундные ряды: три графика, остальные по кнопке, одна легенда на все со значениями графика под курсором. Файлы (логи, JFR). На удалённом стенде ещё блок Layout:
  какая JVM на каком хосте, что это за машина, CPU, GC и heap каждой.
- **Scenarios** — сценарии harness (Java-классы): серверы, клиент и потоки, прогрев/замер, версия и исходники класса
  и его базовых классов из `harness.jar` (`harness.jar list`, читается при старте контроллера).

Страница перерисовывается в свежий контейнер только при изменении содержимого; выбор в выпадающем списке применяется
сразу. Сами обновляются только Queue и страницы с идущей работой (задача, бисект, сравнения); остальные — при переходе,
смене своих фильтров или F5.

## Тесты

`mvn -q test` — 110 тестов контроллера: статистика (вердикты, CI, шум), SQLite-слой, фильтр путей, git-зеркало на временном
репозитории (resolve/log/merge-base/export/`pr/N`), и сквозной конвейер через сервисный слой с `FAKE_BUILD` и
shell-скриптом вместо harness: ABBA до `done` с регрессией, калибровки и порог шума, падение фазы, cancel во время
фазы, восстановление после рестарта, watcher с фильтром/паузой/backlog, compare через merge-base, сравнения
(задача на сценарий, статус по задачам, cancel, delete, повторы), автобисект
(вторая половина при сдвинувшейся первой, два изменения в разных половинах, reuse, spread, confirm, cancel,
stop/resume, рестарт посреди шага). Дымовой тест UI (`everyPageOfTheUiRendersAgainstTheApi`): контроллер с данными
сегмента, двух бисектов и двух сравнений на локальном порту, `node src/test/resources/ui-smoke.mjs` отрисовывает каждую страницу
`app.js` против его API с заглушкой браузера и падает на первой, что бросила исключение; без `node` в PATH или без
права слушать локальный порт тест пропускается.
Git-тесты требуют `git` в PATH; временные репозитории создаются в `java.io.tmpdir` (`-Dtest.tmpdir=…`).
